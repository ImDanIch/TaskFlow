# ПР4: guardrails policy engine

Окремий Python-модуль обчислює рішення `allow`, `warn`, `block` за впорядкованими правилами з `policies.json`. Нових залежностей немає. Оцінювання читає політики й метадані файлової системи, але не читає вміст нотаток і нічого не записує у vault.

## Рішення та приклади

| Операція | Приклад | Рішення |
|---|---|---|
| Читання Markdown | `read`, `Components/SQLite.md` | `allow` |
| Створення нової нотатки | `write`, `Concepts/New.md` (не існує) | `allow` |
| Зміна наявної нотатки | `write`, `Components/SQLite.md` | `warn` |
| Видалення | `delete`, будь-яка нотатка | `block` |
| Вихід за межі vault | `read`, `../outside.md` або зовнішній абсолютний шлях | `block` |
| Секрети | `.env`, `.env.local.md`, `Credentials.md`, `Secrets.md`, `AccessToken.md`, `*.pem`, `*.key` | `block` |
| Метадані | `.git/Note.md`, `.obsidian/Note.md` | `block` |
| Невідома операція або не-Markdown | `execute`, `note.txt` | `block` |

Спрацьовує перше відповідне правило. Обмеження шляхів, секретів і видалення перевіряються перед дозволами та попередженнями. Список чутливих назв у JSON нечутливий до регістру й застосовується до всіх компонентів шляху. Перевіряються також resolved path, symlinks, junctions, hardlinks, Windows ADS, неоднозначні та зарезервовані імена. Абсолютний шлях усередині vault допустимий для evaluator; сам MCP-сервер продовжує приймати лише відносні шляхи.

`allow` означає лише дозвіл політики, а не успішність файлової операції: читання відсутньої нотатки далі завершиться помилкою MCP. `warn` — попередження, не блокування й не інтерактивне погодження.

Програмне використання з кореня TaskFlow:

```python
from pathlib import Path
from guardrails.policy import PolicyEvaluator

policy = PolicyEvaluator(Path("C:/Users/user/TaskFlow-KB"))
result = policy.evaluate("write", "Components/SQLite.md")
print(result.as_dict())
# {'decision': 'warn', 'rule': 'update_note', 'reason': '...'}
```

Інший файл правил можна передати другим аргументом конструктора. Невалідні правила відхиляються; у hook-процесі помилка оцінювання повертає явну заборону без відображення вхідних даних.

## Дослідження підтримки Codex

Перевірено локальні виконувані файли:

- `codex --version`: **0.139.0**; `codex features list`: `hooks stable true`.
- VS Code extension `openai.chatgpt-26.1007.21434-win32-x64`, вбудований Windows runtime: **0.162.0-alpha.17.2**; `hooks stable true`.

[Офіційна документація OpenAI Hooks](https://learn.chatgpt.com/docs/hooks) описує `PreToolUse` для локальних MCP-викликів і project-local `.codex/hooks.json`. Документований спосіб блокування — JSON із `hookSpecificOutput.hookEventName: PreToolUse` та `permissionDecision: deny`. Для попередження використовується `additionalContext`; значення `ask` для цього event наразі не підтримується і тут не використовується.

Отже, **підтримуваний механізм блокування до виконання існує** у локальному Codex. Це не вигаданий hook і не post-execution перевірка. Наявність feature у runtime не підтверджує, що конкретна поточна IDE-сесія вже завантажила hook.

## Мінімальна інтеграція

Створено справжній project-local `.codex/hooks.json` і адаптер `codex_hook.py`; MCP-інструменти не змінювалися. Matcher `^mcp__taskflow_kb__.*$` обмежує інтеграцію інструментами цього сервера.

Відображення рішень:

- `get_note` → операція `read`.
- `ingest_note` → операція `write`.
- `allow` → hook не додає заборону й не обходить звичайні дозволи Codex.
- `warn` → модель отримує попередження через `additionalContext` до виконання; запис дозволений.
- `block` → документований `permissionDecision: deny`.
- `search_notes` та інші невідомі інструменти цього сервера → `deny`: bulk-пошук може повернути вміст секретної нотатки навіть за безпечним query, а pre-hook не може відфільтрувати його результати. Це свідоме обмеження мінімальної інтеграції, а не зміна реалізації MCP.

Адаптер використовує `TASKFLOW_KB_PATH`, а за відсутності змінної — сусідній із TaskFlow каталог `TaskFlow-KB`. Для іншого vault значення в середовищі процесу Codex має збігатися з vault сервера. Значення `env` в окремій MCP-конфігурації не обов'язково передається hook-процесу. У поточному проєкті обидва стандартні шляхи відповідають `C:\Users\user\TaskFlow-KB`.

### Активація та перевірка в Codex CLI

Codex вимагає review і trust для неменеджованих hooks. Відкрийте проєкт як довірений, перезапустіть/перезавантажте сесію Codex, перегляньте й довірте точний hook через `/hooks` у CLI. Використовуйте CLI й IDE зі спільними налаштуваннями користувача. Якщо змінити hook, перевірка trust потрібна знову. Шляхи в command прив'язані до `C:/Users/user/TaskFlow`; при переміщенні проєкту їх потрібно оновити.

Після активації перевірте лише читання:

1. Викличте `get_note` для `Components/SQLite.md` — очікується дозвіл.
2. Спробуйте `get_note` для `.env` — очікується відмова **hook**, без виконання MCP. Перевірте журнал hook/tool: помилка самого сервера не доводить блокування перед викликом.
3. Для перевірки попередження запису використовуйте тільки тимчасовий vault і окрему наявну тестову нотатку, не робочі знання.

**Перевірений результат ПР4:** `PreToolUse` hook активний і довірений у Codex CLI. Спостерігалася live-відмова до виконання MCP:

```text
Tool call blocked by PreToolUse hook: A nonempty note path is required.. Tool: mcp__taskflow_kb__get_note
```

Початковий виклик передав `{"path":"../guardrail_test_nonexistent.md"}`. Правильне ім'я аргументу MCP — **`note_path`**. Hook отримує аргументи в об'єкті `tool_input` і читає `tool_input.note_path`; тому початковий виклик передав evaluator значення `None`. Це помилка аргументу виклику, а не parser hook. Regression-тест через stdin/subprocess підтверджує обидва випадки: `path` → `A nonempty note path is required.`, `note_path` із тим самим шляхом → `Invalid or ambiguous path.`. Другий результат перевірено тестом адаптера, а не повторним live-викликом MCP.

Рішення `allow`, `warn`, `block` перевірено автоматичними тестами. Онтологія TaskFlow-KB: **9 сутностей, 22 зв'язки, 0 помилок**. Obsidian-нотатки та MCP-інструменти не змінювалися; обхід hook trust не застосовувався.

## Межі захисту

Самостійний evaluator лише повертає рішення: споживач повинен застосувати його перед дією. Project hook захищає тільки відповідні MCP-виклики після завантаження й trust. Він не перехоплює довільні shell-команди, прямі файлові операції, інші сервери чи інструменти. Наявного MCP delete-інструмента немає; заборона `delete` перевірена в standalone evaluator, а невідомі MCP-операції блокуються адаптером.

Секрети визначаються за назвами шляхів, не за вмістом: секрет у звичайній `Notes.md` не розпізнається. Локальний процес може змінити файл після перевірки; це не ОС-пісочниця. Правила та hook є локальними редагованими файлами.

За документацією OpenAI, деякі tool paths не покриваються hooks; помилка/timeout hook може не зупинити виклик, навіть якщо адаптер сам повертає явний deny для оброблених помилок. Налаштовані локальні command hooks також не підтримуються для cloud orchestration. Тому ця інтеграція не є універсальною межею безпеки для всіх режимів Codex.
