# ПР6: оркестрація Agent Harness

## Реалізація

Host Codex запускає окремі subagents послідовно: Planner → Coder → Reviewer.
Це три окремі контексти виконання, а не три заголовки однієї відповіді.
`orchestration/workflow.py` реалізує журнал передачі відповідальності:
`Workflow(task).handoff(role, agent_id=..., context=..., rationale=...,
result=..., next_role=...)`. Після фактичного результату host записує handoff;
пропуск Reviewer, неправильний порядок або порожні поля відхиляються.
Reviewer може повернути роботу Coder; лише Reviewer переводить цикл у Complete.
`save(root, relative_path)` перевіряє CodePolicyEvaluator перед збереженням JSON.
Модуль не викликає LLM самостійно: запуск, очікування та передавання повідомлень
виконує host через `collaboration.spawn_agent`, `send_message`, `followup_task`.
Журнал фіксує повідомлені результати; сам по собі він не доводить виконання тестів.

| Роль | Відповідальність та інструкції | Доступ |
|---|---|---|
| Planner | Перевірити відсутність функції, сформувати scope, контракт, ризики, критерії приймання | Читання дозволеного коду/тестів, Guardrails evaluator, MCP get_note відомого дозволеного шляху; запис власного звіту |
| Coder | Виконати план, пояснити рішення, додати й запустити тести, передати фактичний результат | Читання контексту, зміни лише app/tasks.py і tests/test_tasks.py, власний звіт; terminal pytest |
| Reviewer | Незалежний review за taskflow-code-review: код, тести, контракт, Guardrails; accepted або findings | Дозволене читання, MCP get_note, evaluator, terminal pytest; запис звіту, без виправлень коду |
| Host | Передати контекст, зберегти артефакти, організувати доопрацювання, commit/push після прийняття | Workflow, Git, документація й артефакти; права користувача не розширюються |

Доступ задається інструкціями ролей і перевіряється diff/review. Це не окрема
ОС-пісочниця для кожної ролі. Наявний sandbox та політики залишаються чинними.
`block` зупиняє файлову дію; `warn` вимагає diff і релевантних тестів.
Заборонені секрети, БД, agent-конфігурація, видалення, вихід за межі проєкту.
Bulk MCP search не використовується; KB читається через `get_note(note_path=...)`
після PolicyEvaluator. Записів KB немає. Live hook trust цим циклом не атестовано.

## Завдання розвитку

Planner встановив, що GET /tasks має фільтри, але не має пагінації.
Додано необов'язкові `offset` від 0 до `9223372036854775807` (default 0) та `limit` від 1 до 100
(default None). Без limit зберігається попередня поведінка повного списку.
Приклад: `/tasks?status=todo&priority=high&offset=1&limit=2`.
Спочатку застосовуються обидва фільтри, потім сторінка у порядку id.
Некоректні параметри повертають 422; порожня сторінка — `[]`.
Модель, схема БД, залежності не змінюються. Offset pagination не гарантує
незмінної вибірки при паралельному додаванні або видаленні завдань.
Верхню межу offset додано після реального finding Reviewer: SQLite приймає
лише signed 64-bit integer; більші значення тепер відхиляються з 422 замість 500.

## Передавання контексту

Planner передає не лише назву задачі, а контракт сумісності, allowlist,
критерії тестування та причини вибору optional limit. Coder отримує ці критерії
в окремому запуску й передає результати реалізації та тестів. Reviewer отримує
план, звіт Coder і поточний diff, повторно читає код та запускає перевірки.
Спільна робоча директорія усуває копіювання патчів, але потребує послідовних
запусків: одночасних змін одного файла немає. Host працює лише над механізмом
оркестрації, його тестами, документацією та артефактами.

Артефакти `artifacts/orchestration/`: `planner.md`, `coder.md`, `reviewer.md`
містять реальні звіти ролей; `run.json` — структуровані handoff;
`transcript.md` — журнал запусків і отриманих результатів, а не приховані
міркування агентів. Початкова стороння untracked `.agents/` не включається в commit.

## Перевірка

Python усередині sandbox спочатку повідомив про недоступний базовий executable.
Той самий `.venv/Scripts/python.exe` поза sandbox успішно виконав evaluator
і тести. Це обмеження видимості середовища, а не підстава змінювати Guardrails.
Команди з українським виводом використовують `-X utf8`.
Тести API використовують наявну тимчасову SQLite fixture, без робочої БД.
Підсумкові точні результати й exit codes наведено у звіті Reviewer і транскрипті.
Фінальна незалежна перевірка: **218 passed, 1 warning**, exit 0 (49.20s).
Повний фактичний цикл включав доопрацювання: Planner → Coder → Reviewer →
Coder → Reviewer → Complete. Перший review повернув changes_requested через
SQLite overflow; повторний — accepted. Початковий і фінальний звіти збережено
окремо (`reviewer.md`, `reviewer-final.md`).

Повторення: запустити Planner з тим самим scope, передати його результат новому
Coder, потім передати план, diff та результат Coder новому Reviewer. Створити
новий Workflow, записувати handoff лише після завершення відповідної ролі,
при findings повернути Coder і повторити Reviewer. Перед commit перевірити
allowlist, diff і успішні тести; push виконувати лише за дозволом користувача.
