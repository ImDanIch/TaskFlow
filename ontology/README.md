# Практична робота 4: проста онтологія TaskFlow-KB

Онтологія описує типи знань і зв'язки між Markdown-нотатками. Це окремий модуль проєкту: він не змінює FastAPI, MCP-інструменти, конфігурацію Codex або нотатки Obsidian. Guardrails реалізовано окремим модулем: [guardrails](../guardrails/README.md).

## Визначення

Машиночитані визначення містяться у `definitions.json`; валідатор використовує їх як єдине джерело допустимих типів.

| Тип сутності | Призначення | Приклад наявної нотатки |
|---|---|---|
| `concept` | Поняття або архітектурна ідея | `Concepts/REST API.md` |
| `component` | Технологія або складова системи | `Components/SQLite.md` |
| `decision` | Архітектурне рішення | `Decisions/Database Design.md` |
| `glossary` | Термін і визначення | `Glossary/CRUD.md` |

| Тип зв'язку | Напрямок і значення | Приклад моделювання |
|---|---|---|
| `uses` | Джерело використовує ціль | TaskFlow Architecture → SQLite |
| `depends_on` | Джерело залежить від цілі | Database Design → SQLAlchemy |
| `implements` | Джерело реалізує ціль | FastAPI → REST API |
| `related_to` | Джерело пов'язане з ціллю | CRUD → REST API |

Ці приклади демонструють можливу класифікацію. Наявні нетипізовані посилання не отримують автоматично значення `uses`, `depends_on` або `implements`. Усі зв'язки зберігають напрямок джерело → ціль; зворотні зв'язки й логічні висновки не генеруються. Обмежень на комбінації типів джерела та цілі, цикли або самопосилання немає.

## Формат нотаток

Наявний YAML frontmatter підтримується без переписування. Поле `type` визначає сутність; інші поля, наприклад `tags` та `status`, дозволені й не перевіряються цією онтологією.

Приклад **можливого** frontmatter для архітектурної нотатки (приклад лише в документації, у vault не записувався):

```markdown
---
type: concept
tags: [architecture, taskflow]
status: active
relationships:
  - type: uses
    target: Components/SQLite.md
  - type: depends_on
    target: "[[SQLAlchemy]]"
  - type: implements
    target: Concepts/REST API.md
  - type: related_to
    target: Glossary/CRUD.md
---
# TaskFlow Architecture
```

`relationships` — необов'язковий список об'єктів із рівно двома полями: `type` та `target`. YAML frontmatter читається через PyYAML SafeLoader із додатковим відхиленням повторних ключів; довільні Python-об'єкти не конструюються.

Наявні `[[SQLite]]` у тілі нотатки інтерпретуються як `related_to`. Підтримуються також `[[Components/SQLite]]`, `[[SQLite|База даних]]` і `[[SQLite#Розділ]]`: alias і fragment не впливають на пошук цільової сутності. Наявність самого розділу не перевіряється. Однакові ребра усуваються.

Це обмежений розбір wikilinks, а не повний Markdown/Obsidian parser: звичайні Markdown-посилання та `![[embeds]]` не перевіряються; wikilinks усередині прикладів коду можуть також бути враховані. Локальні посилання лише на заголовок `[[#Розділ]]` не підтримуються.

## Правила валідації

1. Файл із frontmatter має містити один із чотирьох допустимих `type`. Невідомий або відсутній тип — помилка.
2. Виняток сумісності: `type: moc` — навігаційна сторінка, не п'ятий тип сутності; вона пропускається з попередженням. Нотатки без frontmatter, наприклад README, також пропускаються. Їхні вихідні посилання не перевіряються.
3. Frontmatter має бути коректним YAML-об'єктом між двома рядками `---`. Некоректний YAML, незакритий блок і повторні ключі — помилки.
4. Кожний явний зв'язок має допустимий тип і рядкову ціль.
5. Ціль повинна посилатися на валідну сутність, а не лише на будь-який файл. Відсутня або неоднозначна ціль — помилка.
6. Шлях із каталогом визначається від кореня vault й має точно збігатися з відносним шляхом сутності. Коротке ім'я шукається за назвою файлу в усьому vault; при дублюванні потрібен повний відносний шлях. Регістр має значення. Суфікс `.md` можна пропустити.
7. Зовнішні й абсолютні посилання, `..` та drive-шляхи не є допустимими ідентифікаторами сутностей. `.git`, `.obsidian`, symlinks і junctions пропускаються під час обходу.

Перевірка має два проходи: спочатку індексує валідні сутності, потім перевіряє та розв'язує зв'язки. `Report` містить `entities`, `relationships`, `errors`, `warnings`. Сканування лише читає файли, без виправлень або запису результатів у vault.

## Встановлення та запуск

Із кореня TaskFlow у PowerShell (Python 3.12+, наявне `.venv`):

```powershell
.\.venv\Scripts\python.exe -m pip install -r ontology/requirements.txt
.\.venv\Scripts\python.exe -m ontology.validator C:\Users\user\TaskFlow-KB
```

Окрема залежність PyYAML потрібна для стандартного YAML frontmatter; власний неповний YAML parser не використовується. Основні й MCP-залежності не змінювалися.

Коди завершення CLI: `0` — помилок немає (попередження дозволені), `1` — помилки онтології, `2` — помилка аргументів або недоступний vault.

Програмне використання:

```python
from pathlib import Path
from ontology.validator import validate_vault

report = validate_vault(Path("C:/Users/user/TaskFlow-KB"))
print(report.errors)
print(report.relationships)
```

## Перевірені результати

Під час ПР4 реальний vault перевірено без запису: **9 сутностей, 22 зв'язки, 0 помилок**. `README.md` і `TaskFlow MOC.md` пропущено з попередженнями. Кількість може змінитися після майбутніх змін vault.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Повний набір після завершення ПР4 (онтологія та guardrails): **147 тестів пройдено**, одне наявне попередження Starlette/HTTPX. Тести онтології використовують тільки тимчасові нотатки й перевіряють усі типи, явні й наявні зв'язки, відсутні та неоднозначні посилання, некоректний YAML, дублікати ключів, виключення навігаційних файлів, CLI-коди та незмінність байтів нотаток.
