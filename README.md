# TaskFlow

Практична робота 4: додано [онтологію TaskFlow-KB](ontology/README.md) із чотирма типами сутностей, чотирма типами зв'язків і read-only валідатором YAML frontmatter та посилань. Перевірений результат: **9 сутностей, 22 зв'язки, 0 помилок**. Реалізовано [guardrails policy engine](guardrails/README.md) із перевіреними рішеннями `allow`, `warn`, `block`. Project-local Codex `PreToolUse` hook активний і довірений у Codex CLI; спостерігалася live-відмова до виконання MCP. Правильне ім'я аргументу MCP — `note_path`, а не `path`: початковий виклик із `path` отримав `A nonempty note path is required.`, тоді як regression-тест із `note_path` підтвердив `Invalid or ambiguous path.` для `../guardrail_test_nonexistent.md`. Повний набір: **147 успішних тестів**. Нотатки vault, FastAPI та MCP-інструменти не змінено.

Практична робота 3: реалізовано й перевірено локальний MCP-сервер TaskFlow-KB через Codex: `search_notes`, `get_note`, `ingest_note`. Також через GitHub MCP успішно прочитано `ImDanIch/TaskFlow/README.md`. Повний набір тестів після додавання MCP: **78 успішних тестів**. Встановлення, запуск, межі доступу й результати перевірки описано в [mcp_server/README.md](mcp_server/README.md). Це реалізація MCP-інтеграцій, а не всіх можливостей майбутнього agent harness.

TaskFlow — навчальний REST API для керування особистими завданнями. Проєкт демонструє побудову локального застосунку на FastAPI, збереження даних у SQLite, валідацію запитів і автоматизоване тестування. Він також використовується як навчальна основа для формування вимог до середовища роботи AI-агента (agent harness).

API вже реалізований. Власний агентний harness у цьому репозиторії ще не реалізований; його початкові вимоги наведено окремо нижче.

## Функціональні вимоги та їх реалізація

1. **Створення завдання:** `POST /tasks` приймає JSON і повертає створене завдання з кодом `201`.
2. **Перегляд списку:** `GET /tasks` повертає всі завдання, впорядковані за `id`; порожній список повертається як `[]`.
3. **Перегляд за ідентифікатором:** `GET /tasks/{task_id}` повертає завдання або `404`, якщо його немає.
4. **Часткове оновлення:** `PATCH /tasks/{task_id}` змінює лише передані поля; для відсутнього завдання повертає `404`.
5. **Видалення:** `DELETE /tasks/{task_id}` повертає `204` без тіла відповіді або `404`, якщо завдання не знайдено.
6. **Статуси:** підтримуються `todo`, `in_progress`, `done`; початкове значення — `todo`.
7. **Пріоритети:** підтримуються `low`, `medium`, `high`; початкове значення — `medium`.
8. **Фільтрація:** `GET /tasks` підтримує необов'язкові параметри `status` і `priority`. Якщо задано обидва, застосовуються обидві умови, наприклад `/tasks?status=todo&priority=high`.

Додатково реалізовано `GET /health`, який повертає `200` і `{"status": "ok"}`.

### Дані та валідація

| Поле | Опис |
|---|---|
| `id` | Цілочисельний первинний ключ, формується базою даних. |
| `title` | Обов'язковий непорожній рядок; API прибирає пробіли на початку та в кінці. |
| `description` | Необов'язковий текст, допускає `null`. |
| `status` | Один із трьох підтримуваних статусів. |
| `priority` | Один із трьох підтримуваних пріоритетів. |

Невідомі поля запиту, некоректні типи, порожня назва та неприпустимі значення повертають `422`. У `PATCH` пропущені поля зберігають попередні значення; `description: null` очищує опис. Значення `null` для `title`, `status` і `priority` заборонені. Порожній об'єкт `{}` у `PATCH` допустимий і не змінює завдання.

## Нефункціональні вимоги

| Вимога | Поточна реалізація та межі |
|---|---|
| Надійність | SQLite зберігає дані між перезапусками. Таблиці створюються під час запуску; повторна ініціалізація безпечна. Записи фіксуються транзакціями, обмеження БД перевіряють назву та допустимі статуси й пріоритети. Автоматичних міграцій і резервного копіювання немає. |
| Підтримуваність | Невеликі модулі з окремими відповідальностями: запуск, база даних, модель, схеми та маршрути. Використовується синхронний SQLAlchemy без додаткових сервісних шарів. |
| Тестованість | pytest перевіряє API та базу даних. Кожний тест отримує окрему тимчасову SQLite-базу, тому робочий `taskflow.db` не використовується. |
| Безпека | Pydantic перевіряє вхідні дані, невідомі поля відхиляються, SQLAlchemy формує параметризовані запити. Автентифікацію й авторизацію не реалізовано: API призначений для локального навчального використання. |

## Технології та середовище розробки

- Python; у поточному середовищі розробки використано Python 3.13.5.
- FastAPI — HTTP API та автоматична документація OpenAPI.
- Pydantic — схеми запитів і відповідей; встановлюється як залежність FastAPI.
- Uvicorn — локальний ASGI-сервер.
- SQLAlchemy — синхронна ORM і керування сесіями.
- SQLite — локальна файлова база, без окремого сервера.
- pytest і HTTPX/FastAPI TestClient — автоматизовані тести.
- Windows, PowerShell, VS Code, OpenAI Codex і Git — середовище та інструменти розробки.

Прямі залежності перелічено в `requirements.txt`; їхні версії наразі не зафіксовані. Фронтенд, Docker та зовнішня база даних не використовуються.

## Архітектура і структура файлів

Обробка запиту: **HTTP → маршрут FastAPI та валідація Pydantic → сесія SQLAlchemy → SQLite → відповідь за Pydantic-схемою**.

```text
TaskFlow/
├── app/
│   ├── __init__.py       # Python-пакет застосунку
│   ├── main.py           # FastAPI, lifespan, підключення маршрутів, /health
│   ├── database.py       # Шлях до БД, engine, Base, SessionLocal, get_session
│   ├── models.py         # ORM-модель Task та обмеження даних
│   ├── schemas.py        # TaskCreate, TaskUpdate, TaskResponse
│   └── tasks.py          # CRUD-маршрути, фільтрація, обробка 404
├── tests/
│   ├── conftest.py       # Ізольована тимчасова БД для кожного тесту
│   ├── test_health.py    # Перевірка /health
│   ├── test_database.py  # Ініціалізація, обмеження, збереження даних
│   └── test_tasks.py     # CRUD, фільтри, валідація та помилки
├── requirements.txt      # Залежності
├── .gitignore            # Правила ігнорування Git
└── README.md             # Документація
```

Файл `taskflow.db` створюється в корені проєкту під час запуску застосунку. Його шлях обчислюється від розташування `database.py`, тому не залежить від поточної робочої директорії. `get_session` надає окрему сесію для запиту та закриває її після обробки. `Base.metadata.create_all` створює відсутні таблиці, але не виконує міграції наявної схеми.

## Встановлення

Нижче наведено команди для PowerShell. Потрібен встановлений Python із підтримкою `venv` та `pip`.

```powershell
cd C:\Users\user\TaskFlow
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Якщо проєкт розташований в іншому каталозі, змініть шлях у команді `cd`. Активація віртуального середовища не обов'язкова: команди безпосередньо використовують його Python.

## Запуск API та Swagger

Із кореня проєкту виконайте:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

- API: <http://127.0.0.1:8000> (окремого маршруту `/` немає).
- Перевірка роботи: <http://127.0.0.1:8000/health>.
- Swagger UI: <http://127.0.0.1:8000/docs>.
- OpenAPI-схема: <http://127.0.0.1:8000/openapi.json>.

У Swagger відкрийте `POST /tasks`, натисніть **Try it out** і надішліть:

```json
{
  "title": "Вивчити FastAPI",
  "description": "Виконати навчальне завдання",
  "status": "todo",
  "priority": "high"
}
```

Для перевірки збереження даних запам'ятайте отриманий `id`, зупиніть сервер через `Ctrl+C`, запустіть його знову й виконайте `GET /tasks/{task_id}`. Створене завдання залишиться в `taskflow.db`.

## Запуск тестів

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тести охоплюють health endpoint, створення таблиць при запуску, повторну ініціалізацію, збереження завдання після закриття та повторного створення engine, обмеження моделі, CRUD, окремі й комбіновані фільтри, відповіді `404` та `422`.

Останній перевірений результат під час реалізації API: **56 тестів пройдено**. Встановлені версії Starlette/HTTPX також видали одне попередження про застарілу інтеграцію TestClient; воно не спричинило падіння тестів.

## Використання OpenAI Codex у VS Code

Розробка виконувалася поетапно за текстовими завданнями користувача в контексті роботи з VS Code та Codex. Спочатку агент перевірив файли й Git-стан проєкту та запропонував просту архітектуру. Після схвалення користувачем агент створював потрібні модулі, додавав тести та запускав їх через термінал.

Для кожного етапу користувач задавав обсяг робіт і обмеження. Агент зберігав наявну функціональність, повідомляв перелік змін і результати перевірок. Коли на початковому етапі Python був недоступний, це було явно зазначено; після появи віртуального середовища наступні етапи перевірялися тестами. Коміти та відправлення змін у віддалений репозиторій агент не виконував.

### Три завершені завдання за участю агента

1. **Каркас FastAPI та health endpoint.** Створено пакет `app`, застосунок FastAPI, `GET /health`, список залежностей і базовий тест. Наявні README та `.gitignore` на цьому етапі збережено.
2. **SQLite та модель Task.** Додано engine, фабрику сесій, модель із перевірками та значеннями за замовчуванням, ініціалізацію таблиць під час запуску й тести збереження даних. Після цього етапу пройдено 21 тест.
3. **CRUD API з валідацією та тестами.** Додано Pydantic-схеми, п'ять маршрутів роботи із завданнями, фільтрацію, обробку відсутніх записів і некоректних даних. Повний набір після цього етапу: 56 успішних тестів.

## Початкові вимоги до AI agent harness — заплановано

Цей розділ описує вимоги до майбутнього середовища керування агентом. Це не реалізовані можливості API TaskFlow і не окремий готовий компонент поточного репозиторію. Використання файлів, термінала та Git під час розробки саме по собі не означає наявності власного harness.

| Запланована можливість | Початкова вимога |
|---|---|
| Доступ до файлів проєкту | Агент має читати структуру й код та вносити зміни лише в межах дозволеного завдання й робочої області. |
| Виконання тестів | Середовище має запускати pytest, отримувати код завершення й результати та повідомляти про помилки або неможливість перевірки. |
| Інтеграція з Git | Агент має переглядати статус і diff; коміти, push та інші операції повинні відповідати наданим дозволам. |
| Доступ до бази знань | У ПР3 реалізовано доступ до окремого Obsidian vault TaskFlow-KB через MCP; пошук, читання та запис перевірено викликами з Codex. Керування цим доступом як частиною власного harness залишається запланованим. |
| Контроль безпеки та перевірка змін | Потрібні межі доступу, контроль ризикованих дій, перегляд diff і перевірка тестами перед прийняттям змін. Успішні тести не замінюють перегляд людиною. |
| Повторно використовувані skills | Середовище має підтримувати набори інструкцій для типових завдань; власних skills для TaskFlow наразі не додано. |
| Мультиагентні процеси | Потрібна можливість розподілу незалежних завдань між агентами, координації змін і спільної перевірки результату. Такий процес у TaskFlow ще не реалізовано. |
